# Define the 3D production runtime and asset contract

Type: grilling
Status: resolved

## Question

What browser support, adaptive-quality levels, fallback behavior, asset naming and versioning, material slots, loading budgets, interaction guarantees, rendering validation, and compatibility rules make the configurator production-safe?

## Answer

The production configurator is an accurate visual planning tool, not manufacturing CAD. It must faithfully represent the selected layout, major geometry, finish identity, material class, and approved views, while clearly excluding installation validation, millimeter planning, appliance specification, and any promise that an illustrative render is the delivered product. Product and commercial truth remain in the Kitchen Configuration, Release Bundle, and later Authoritative Quote.

Interactive 3D targets current production Chrome, Edge, Safari, and Firefox on desktop and mobile when WebGL2 and runtime capability and stability checks pass. No WebGL1 implementation is maintained. Every configuration workflow—including selection, saving, sharing, Price Indication, and Quote Request—continues through a Deterministic Visual Fallback when stable 3D is unsupported, slow, or lost. Exact approved raster coverage is distinguished from illustrative layout/material compositions; an approximation is never labelled exact.

The engine receives one validated Render Specification derived from the Kitchen Configuration and pinned Release Bundle. It resolves Semantic Scene Roles, material assignments, visibility, camera keys, and Quality Profile without querying Sanity, pricing, Projects, commerce, or mutable Product Definition Drafts. Presentation state such as orbit pose, atmosphere, camera, path tracing, and Quality Profile does not enter configuration identity, revision hashes, or commercial records.

Production assets cannot rely on generic mesh names, geometric heuristics, material indices, or first-option fallbacks. An Asset Manifest explicitly maps required Semantic Scene Roles to named nodes and material slots. Missing, duplicate, unknown, or incompatible required roles block Release Candidate activation. An unexpected runtime mismatch produces a visible fallback or unavailable state plus telemetry rather than a plausible but incorrect visual.

The current `kitchen-line.glb` remains a prototype fixture. Its generic nodes, shared material, absent UVs and textures, and runtime classification heuristics do not satisfy the production contract. The 28.6 MB apartment asset is also unsuitable for automatic delivery. Production requires newly prepared models with correct units, origin, bounds, transforms, normals, tangents, UVs where required, explicit configurable and fixed geometry, stable semantic mappings, and approved quality variants.

Models, textures, environment maps, raster fallbacks, manifests, and other production assets are immutable and content-hashed. Asset Manifests preserve checksums, dimensions, color space, compression, license and provenance, runtime characteristics, compatibility, `renderContractVersion`, required glTF features/extensions, and supported engine range. Corrections produce new manifests and Release Bundles; mutable replacement at an existing URL is forbidden.

The Studio Scene is the canonical comparison view with controlled cameras and lighting. Atmospheric scenes are optional and use the same Render Specification. They cannot alter configuration meaning, hide selectable geometry, or replace the Studio Scene. Stable camera keys and desktop/mobile framing constraints live in the Asset Manifest and validate against model bounds. Shared configurations open canonically unless a later separate presentation-state contract is introduced.

Quality Profiles are selected from capability, preferences, network hints, memory/texture limits, a render probe, and observed stability rather than viewport width alone. The outcomes are Deterministic Visual Fallback, low interactive 3D, standard interactive 3D, and enhanced presentation. A session starts conservatively, downgrades on sustained frame or context instability, and does not oscillate during interaction. LOD and quality changes may reduce texture/geometric detail, shadows, reflections, antialiasing, and post-processing, but must preserve selectable parts, silhouettes, finish identity, visibility, and roles.

Stable raster rendering is canonical and required. Path tracing is an optional enhanced presentation for capable devices after canonical interactivity and explicit customer action or controlled idle enhancement; it is never required for configuration or Source Capture. Atmospheric assets load only after Studio interactivity and explicit request. Enhanced textures, path-tracing dependencies, and room assets are deferred, while the canonical low/standard Studio variant loads first. Offline/service-worker asset caching is outside the First Production Release.

Initial Release Candidate budgets are 6 MB compressed critical transfer for the canonical Studio Scene, 128 MB low-profile and 256 MB standard-profile GPU texture allocation, 150,000 rendered triangles and 100 draw calls for the canonical kitchen, and 12 MB compressed plus 500,000 rendered triangles after LOD/culling for an optional atmospheric scene. Production textures are capped at 2K unless an approved measured exception exists. The production quality-bar decision may tighten these ceilings.

Runtime state is explicit: checking, loading, interactive, fallback, or unavailable. Deterministic fallback appears while assets load and within one second on the defined profiles. Timeout or load failure offers one controlled retry before maintaining the workflow in fallback. One renderer recovery follows WebGL context loss; repeated loss fixes the session to fallback. Canonical 3D targets p75 interactivity within five seconds on the defined mid-tier mobile/fast-4G profile and three seconds on desktop. Selection feedback begins within 100 ms and reaches its settled material state within 300 ms. Low profile sustains at least 30 FPS; standard targets at least 45 FPS, with sustained misses causing downgrade.

Release validation blocks activation unless it verifies immutable asset closure and checksums, supported glTF features and decoder availability, units/origin/bounds/transforms, shading and UV correctness, role cardinality and slot mapping, transfer/triangle/draw-call/memory/texture budgets, camera framing, fallback coverage, every permitted configuration combination, absence of mutable/external dependencies, licensing/provenance, and clean loading/render smoke tests.

Each release also produces deterministic raster reference images for representative configurations, every approved camera, desktop and mobile framing, and each Quality Profile. Automated visual comparison runs on current Chromium, Firefox, and WebKit paths, and intentional changes require human product/design approval. Engine upgrades run the historical compatibility suite before deployment and cannot reinterpret an existing manifest. If an old interactive contract can no longer run safely, retained display data and approved fallback imagery preserve historical interpretation without silent migration.

A Source Capture uses stable raster rendering only after asset and material readiness, an approved camera key, fixed dimensions, and removal of UI overlays. Its provenance records the Render Specification hash, Release Bundle, Asset Manifest, renderer version, camera key, Quality Profile, capture settings, and image checksum. Customers may choose among approved cameras but arbitrary orbit poses do not become production provenance.

The canvas is never the only operable or understandable interface. Every selection remains available through labelled keyboard controls and textual summaries; camera actions have keyboard alternatives and reset; reduced-motion preferences suppress nonessential transitions. Fallback users retain the complete workflow, and decorative 3D detail does not create an unusable accessibility tree.

Production cannot depend silently on deprecated APIs, private path-tracer internals, hard-coded authoring-tool names, or default-option substitutions. Those dependencies must be removed or isolated behind explicit tested compatibility code before release. Dependency upgrades require browser, compatibility, smoke-render, and visual-regression verification.

Privacy-safe observability records capability decisions, initial and downgraded Quality Profiles, asset timings and failures, fallback reasons, context loss, sustained frame performance, manifest/engine incompatibility, camera/view use, and Source Capture readiness failures. It never records full Kitchen Configuration payloads or customer imagery as telemetry.

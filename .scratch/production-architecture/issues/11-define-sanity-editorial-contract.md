## Question

Which page, localization, presentation, Product Definition reference, preview, publication, and page-builder responsibilities belong to Sanity, and what adapter prevents Sanity document shapes from leaking into the configurator engine or transactional modules?

## Answer

Sanity is a conditional editorial system, not a system of record for runtime configuration or customer activity. It may own non-personal Editorial Content: localized Editorial Pages, navigation, site settings, SEO inputs, editorial media selection, and Product Definition Drafts. It may not store Customer Accounts, Projects, Kitchen Configurations, Configuration Revisions, Generated Photos, Quote Requests, payments, behavioral/customer data, confidential product files, or production 3D assets. Sanity adoption requires an explicit DPA, transfer-impact, and subprocessor review that accepts this restricted scope because Sanity currently documents Google Cloud processing in Belgium as primary and in the United States, plus other non-EU subprocessors. A policy requiring zero US processing for any project information disqualifies Sanity and triggers selection of an EU-hosted CMS. See [Sanity's current subprocessor disclosure](https://www.sanity.io/legal/third-party-sub-processors).

Editorial Pages use linked document-level localization. German lives at `/`; later English and Spanish live at `/en` and `/es`. Each translation independently owns its slug, content, SEO, media accessibility text, and publication state. Missing translations remain unavailable and are excluded from navigation, sitemaps, canonical alternatives, and `hreflang`; the runtime never mixes German fields into another locale. Small shared labels and product metadata may use field-level localized values.

The page builder is a curated, versioned union of Page Blocks. Editors choose block order, content, approved variants, and editorial media, while code owns renderers, layout, accessibility, responsive behavior, and motion. Unknown or invalid block versions prevent publication instead of disappearing at runtime, and older renderers remain supported until still-published documents are migrated. A Configurator Block contains only editorial presentation and a stable `productKey`; the application resolves that key to the active Release Bundle for a new configuration. It never embeds rules, numeric pricing, Product Definition Drafts, or Asset Manifest details.

Sanity supplies localized slug and SEO inputs, but the application owns locale prefixes, reserved routes, collisions, canonical and `hreflang` output, redirect enforcement, sitemap eligibility, and all functional routes. Published slug changes require a validated redirect from the old localized URL; removal requires a redirect or explicit-gone decision. Sanity manages only publication-ready editorial media and its localized alt text, caption, focal point, and crop. Sanity documents that assets remain publicly retrievable even for a private dataset, so customer uploads, confidential files, generated photos, GLBs, textures, environment maps, and other production assets use their designated EU object storage. See [Sanity's data-safety guidance](https://www.sanity.io/docs/content-lake/keeping-your-data-safe).

The `EditorialContent` Module Interface is the runtime seam. It offers the equivalent of `loadPage(locale, slug, mode)` and `loadSiteChrome(locale, mode)` and returns application-owned editorial models. A Sanity Adapter performs GROQ queries, reference resolution, validation, and normalization; the current local content becomes a temporary second Adapter during incremental migration. Sanity document IDs, references, image objects, drafts, and query-result types do not cross the seam. Product release publication is a separate Module rather than another editorial-content method.

Production reads Sanity's `published` perspective through a server-only least-privilege credential. Editorial Preview uses the authenticated `drafts` perspective, renders against the active Release Bundle, is uncached and `noindex`, and disables all external/customer side effects. Release Candidate Preview instead renders an explicitly validated application-owned Release Candidate. Sanity documents these distinct perspectives and their caching behavior in its [preview guidance](https://www.sanity.io/docs/content-lake/presenting-and-previewing-content).

Ordinary Editorial Page publication only requests cache invalidation or revalidation; it cannot activate configurator rules, assets, or pricing. The previous known-good page remains available until replacement validation and revalidation succeed. A separate Request Release action snapshots and normalizes a Product Definition Draft, validates rules and references, assembles a Release Candidate with its compatible Asset Manifest and applicable Price Book Release, gathers product and applicable commercial approval, and lets a separately authenticated Release Manager atomically activate the Release Bundle in Postgres. Sanity may display status and opaque result references but remains non-authoritative.

The initial environment model uses a private `production` dataset for real editorial documents and drafts and a `development` dataset containing synthetic content for schema work, migrations, and tests. Staging reads the published production perspective unless an authorized editor explicitly enters preview; no manually synchronized third dataset is introduced yet. Private datasets are a paid Sanity capability according to the [dataset documentation](https://www.sanity.io/docs/content-lake/datasets).

Contributors create drafts, Editors publish ordinary Editorial Pages, and Administrators or Developers are tightly limited. Sanity roles cannot activate Release Bundles. This uses Sanity's built-in roles without making Enterprise custom roles an architectural prerequisite; the [current roles documentation](https://www.sanity.io/docs/content-lake/roles-concepts) identifies Contributor and Editor capabilities and reserves custom roles for Enterprise. Published-content reads, draft-preview reads, optional release-status writeback, and webhook verification use distinct environment-specific, least-privilege, server-only credentials or secrets.

If Sanity is unavailable, known public pages serve their last known-good cached editorial models. Uncached pages and preview fail visibly rather than borrowing local or German content; the configurator continues from the active Postgres Release Bundle. Schemas and transformations live in Git. Daily production-dataset and referenced-editorial-asset exports go to encrypted EU object storage with 30-day retention, and the team rehearses restoration or import at least quarterly so the application-owned editorial models remain reconstructible without Sanity.
